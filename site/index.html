背景与痛点：门店商业团队每周需对每个 HFB（高层级商品分类）做业绩复盘—— 跨 ONLINE/OFFLINE 多渠道、跨 HFB→PA→Family→Article 四个层级、读数十个指标，再人工归因写结论。 单份周报约 4 小时，且不同分析师口径不一。

方案：一键生成「业绩总结 + 渠道分析 + Sales Tree 漏斗 + 异动商品归因（含 ML 归因、销量预测、潜力商品标记）」的结构化周报，报告不止陈述， 直接指导补货 / 推广 / 陈列行动。

五层诊断流水线

┌─────────────────────────────────────────────────────────────┐ │ ① 数仓层 5 张预聚合周表统一指标口径（ind.LY / Rolling 4wks） │ │ ② 文本化层 for_human / for_llm 双轨：数字只由代码计算 │ │ ③ 分析层 规则引擎 + LLM 两段式对话（业务词典 prompt） │ │ ④ ML 层 SHAP 归因 · 7 天销量预测 · 潜力商品规则识别 │ │ ⑤ 渲染层 报告装配 → HTML（生产环境为 PDF + IM 推送） │ └─────────────────────────────────────────────────────────────┘
核心设计解决的问题
数字全部由代码计算，LLM 只负责语言组织从架构上杜绝 LLM 算错数的幻觉
for_human / for_llm 双轨渲染人读明细与模型输入互不污染
业务术语词典 prompt + few-shot 格式约束结论可复现、结构稳定可直接排版
负向业务约束（门店无定价权）结论符合业务常识，不误导一线
规则引擎兜底（无 Key / LLM 故障自动降级）演示与服务永不中断

技术取舍

取舍原因
ODPS 数仓 → 确定性 Mock 数据生成器剥离内网依赖；schema 与线上一致，分析代码零改动
四模型融合归因 → 单模型 LightGBM+SHAP（默认关闭）演示速度；SHAP 缺失时相关系数兜底
Prophet 预测 → 按星期均值轻量外推依赖重、慢；轻量版秒级出结果
graphviz Sales Tree → 纯 HTML/CSSgraphviz 需系统二进制，不可移植
wkhtmltopdf PDF → HTML 报告 + 浏览器打印硬编码系统路径，不可交付
iframe 嵌入 + 新窗口备用入口避免 Streamlit 休眠或 iframe 限制影响展示

数据与隐私声明

  • 本站点与 Demo 使用确定性仿真数据（时间锚点 2025-07-06，仿真门店）， 不含任何真实经营数据；
  • 不配置 API Key 即可完整演示，结论文字由内置规则模板生成；
  • 如选择填入自有 LLM API Key：Key 仅保存在当前浏览器会话内， 不写入文件、日志、URL 或报告；Key 会发送到 Streamlit 服务端再转发给模型服务商， 建议使用低额度、可撤销的专用 Key；
  • 报告中的文字说明由所示模型或离线模板生成，所有数字由代码计算；
  • 原始系统运行于企业数仓之上，公开版本已移除全部凭证、内网地址与真实输出。
